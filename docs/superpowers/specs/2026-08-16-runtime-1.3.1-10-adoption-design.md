# Adopting executorch-runtime-dist v1.3.1-10

**Date:** 2026-08-16
**Status:** approved design

Upstream `executorch-runtime-dist` v1.3.1-10 adds three things this project wants: an OpenVINO
delegate on `linux-x86_64`, a read-only XNNPACK workspace-size backend option, and a fixed
selector function in the generated CMake pin. This spec decomposes their adoption into three
sequenced units of work and specifies the first two. The third gets its own design cycle.

## Sequence

| Step | Work | Depends on | User-visible |
|---|---|---|---|
| **0+A** | Bump 1.3.1-6 → 1.3.1-10 by adopting the generated pin | — | no |
| **B** | XNNPACK workspace-size metric | 0+A | yes (additive) |
| **C** | OpenVINO as a supported feature | 0+A | yes (own spec) |

Two findings drive this ordering.

**The bump and the pin adoption are one change.** Upstream publishes `EtRuntimePin.cmake` as a
per-release generated asset, so pasting the v1.3.1-10 file *is* the version bump. Sequencing them
separately would mean hand-transcribing the v1.3.1-10 rows and deleting that work one commit later.

**OpenVINO does not leak into step 0+A.** Backends are linked explicitly
(`CMakeLists.txt:35,49` — `executorch xnnpack_backend`), so `libopenvino_backend.a` shipping in the
linux-x86_64 tarball does not enter `_core.so` without a deliberate `target_link_libraries` line.
The wheel does not grow, `registered_backends()` does not change, and the nm guard needs no new row
until step C opts in.

B precedes C because it is small, independently valuable, and is the cheapest proof that the new
tarball is actually live: the workspace option does not exist in v1.3.1-6 at all.

## Step 0+A — bump via the generated pin

### Rationale

`cmake/RuntimePin.cmake` currently hand-transcribes the upstream pin as fully-resolved literals,
carrying a ~15-line comment explaining that the version vars and the URL literals must be kept in
sync by hand. v1.3.1-10 makes that transcription actively dangerous: it adds a
`windows-x86_64-static` (`/MT`) row alongside `windows-x86_64` (`/MD`). Per upstream's
`docs/handover-windows-static-cxx17.md`, the `/MD` row is the correct one for CPython extensions —
it must match CPython's own CRT — and `-static` exists for JNI consumers. A transcription error
here produces a CRT mismatch, not a build failure.

### Changes

**`cmake/EtRuntimePin.cmake`** — new, vendored verbatim from the release:

```
gh release download --repo measly-java-learning/executorch-runtime-dist \
  --tag v1.3.1-10 --pattern 'EtRuntimePin.cmake' --dir cmake/
```

Marked generated / do-not-edit / re-download to bump. Provides `ET_RUNTIME_VERSION`,
`ET_RUNTIME_ET_VERSION`, all `ET_RUNTIME_URL_*` / `ET_RUNTIME_SHA256_*` rows, the
`et_runtime_dist_url(variant platform out_url out_sha)` selector, and the optional
`ET_RUNTIME_OPENVINO_{VERSION,PLATFORM,URL,SHA256}` block that step C consumes.

**`cmake/RuntimePin.cmake`** — reduced to what is genuinely ours: the existing platform-detection
block (unchanged), then

```cmake
include(${CMAKE_CURRENT_LIST_DIR}/EtRuntimePin.cmake)
set(ETNP_ET_VERSION "${ET_RUNTIME_ET_VERSION}" CACHE STRING "Pinned ExecuTorch version")
set(ETNP_RUNTIME_VERSION "${ET_RUNTIME_VERSION}" CACHE STRING "Pinned runtime package revision")
# windows-x86_64 is the /MD row, deliberately: a CPython extension must match CPython's
# own CRT. windows-x86_64-static (/MT) exists for JNI consumers -- not for us.
if(NOT ETNP_RUNTIME_PREFIX)
  et_runtime_dist_url("${ETNP_RUNTIME_VARIANT}" "${_ETNP_PLATFORM}" _ETNP_URL _ETNP_SHA256)
  # FetchContent block unchanged
endif()
```

The version vars now derive from the pin rather than duplicating it, so the sync hazard the old
NOTE warned about ceases to exist; that NOTE is deleted. The local `FATAL_ERROR` for an unknown
variant/platform is also deleted — `et_runtime_dist_url()` raises a better one naming both values.

**`.github/workflows/qa-gate.yml`** — the URL scrape at line 46 repoints from
`cmake/RuntimePin.cmake` to `cmake/EtRuntimePin.cmake`. The generated file still carries literal
URLs, so the pre-CMake scrape contract survives. The existing pattern
(`https://[^"]*logging-${platform}\.tar\.gz`) already excludes the `-static` row because of its
trailing `\.tar\.gz` anchor; this is correct by accident, so it gets an explicit comment recording
that the exclusion is intentional.

**USDT re-vendor** — verification only, not a change. `git diff v1.3.1-6..v1.3.1-10 -- extras/
scripts/check-usdt-notes.sh` is empty upstream, so the probe contract did not move.
`docs/usdt-tracepoints.md` and `scripts/check-usdt-notes.sh` are confirmed current rather than
rewritten. Re-run the diff at implementation time rather than trusting this line.

### Verification

Existing gates, all of which must pass unchanged:

- `python -m pytest tests/`
- leak harness (ASan/LSan), 500 iters
- race harness (TSan) under `setarch -R`
- wheel build on linux-x86_64, linux-aarch64, windows-x86_64
- CI `gh attestation verify` against the new SHAs

Two items require positive verification rather than assumption:

1. **`native_tests/` standalone configure.** Those do their own `find_package(ExecuTorch)` and
   resolve the prefix relative to `RuntimePin.cmake`'s own location. `CMAKE_CURRENT_LIST_DIR` is
   the right primitive for the new `include()`, but only an actual leak/race harness run proves the
   standalone path resolves.
2. **The Windows row.** Confirm the fetched Windows tarball is the `/MD` one and that
   `build-wheels.yml`'s vendored-`msvcp140` / `vcruntime140_threads` assertions still pass. If the
   `/MT` row were selected, those DLLs would vanish from the wheel and the gate would fail closed.

### Rollback

One commit, one revert. No API surface moves.

## Step B — XNNPACK workspace-size metric

### Contract

Backend `XnnpackBackend`, key `workspace_size_bytes`, read via
`executorch::ET_RUNTIME_NAMESPACE::get_option`, value extracted with `std::get_if<int>`.
`XNNPACKBackend.h` is not an installed header, so both strings are hardcoded.

Semantics that shape the API and the test: the value is **0 until the first XNNPACK-delegated
method loads** (the arena is created lazily during delegate init); it is **process-wide** (the
build pins `EXECUTORCH_XNNPACK_SHARED_WORKSPACE=ON`, so it must never be summed across instances);
it is a **high-water mark including alignment padding**, never shrunk; and it is **read-only**
(`set_option` returns `InvalidArgument`).

This option is a vendored patch in this distribution, not upstream ExecuTorch. Code depending on it
will not build against an unpatched ExecuTorch. That constraint is recorded in the C++ source
comment, not only here. The patch is applied to the XNNPACK delegate on every platform this
project ships (see Windows, below).

### Changes

**`src/et_core/`** — `int xnnpack_workspace_size_bytes();` as a free function alongside
`registered_backends()` / `operator_names()` in `et_core.h`. A non-`Ok` error or a non-`int`
variant raises `EtException`, rather than the upstream doc's `-1` sentinel: this codebase's error
contract is exceptions with an `ErrorKind`, and a sentinel would be silently mistaken for a byte
count.

**`src/binding/`** — thin wrapper exposed as `_core.xnnpack_workspace_size_bytes()`. Releases the
GIL around the call, which synchronizes with delegate init.

**`executorch_numpy_runtime/`** — a top-level `xnnpack_workspace_size_bytes()`.

It is deliberately **not** a key in `runtime_info()`. That function reports static capability
description — version, backends, operators, dtypes. A mutable high-water mark reading `0` before
the first delegated load, sitting beside `supported_dtypes`, would read as broken capability
reporting rather than as correct lazy-init behaviour.

### Test

The assertion is the *transition*, not the value: read before any load and assert `0`; load and run
an XNNPACK-delegated fixture; read again and assert `> 0`. The absolute number is not stable across
runs or platforms because of alignment padding and high-water semantics, so nothing asserts on it.

Because the metric is process-wide and monotonic, this test must not share a process with other
tests that load delegated models, or the "before" read will be non-zero. It runs in its own
subprocess.

### Windows

The metric is available on Windows and the test is **not** platform-gated.

The option belongs to the `XnnpackBackend` delegate, not to core, and upstream's
`build-runtime.sh:206-209` applies `patch-et-xnnpack-workspace.sh` unconditionally — "Not guarded
by platform: XNNPACK builds on every platform we ship." `build-runtime.ps1` is only an environment
shim that invokes that same script under Git Bash, so there is no Windows recipe that could skip
the patch.

The "core-only" note on the Windows row (`RuntimePin.cmake:61-62`) means no optimized/quantized ops
libs and no ETNPExtras. The XNNPACK delegate itself ships on every platform, which is why
`CMakeLists.txt:35` requires `xnnpack_backend` unconditionally and `tests/test_meta_info.py`
already asserts `XnnpackBackend` registers on Windows.

`executorch::ET_RUNTIME_NAMESPACE::get_option` is core-runtime backend-options API present in every
tarball. Its availability is a link-time fact — the build succeeds or fails loudly — so it needs no
runtime gate.

## Step C — OpenVINO: scope boundary only

C is a subsystem, not a change, and gets its own brainstorm → spec → plan cycle. This section fixes
its edges so 0+A and B can proceed without prejudging it.

### Decided

- **Fully supported feature**, not merely linked-and-undocumented.
- **`linux-x86_64` only.** The delegate ships in that tarball alone.
- **`openvino==2025.4.1`, exact.** The published fixture asset is OpenVINO-version-coupled
  (`etnp-openvino-fixtures-<etver>-<ovver>`), and a `.pte` embeds a precompiled OpenVINO blob, so a
  range would let a rebuild import a blob-incompatible runtime — surfacing at model load, not at
  install.
- **Extra plus operator override.** `executorch-numpy-runtime[openvino]` installs OpenVINO and the
  package resolves `OPENVINO_LIB_PATH` from inside the installed wheel; an already-set
  `OPENVINO_LIB_PATH` always wins, so upstream's hash-pinned bundle and system installs work
  untouched. The check is an explicit `if "OPENVINO_LIB_PATH" not in os.environ`, never
  `setdefault`, whose eager default would raise when the pip wheel is absent even though the
  variable is already correct.
- **Fixture: committed bytes plus a manifest.** The four members (`openvino_tiny.pte`, `in.bin`,
  `out.bin`, `shape`) are unpacked into `tests/models/openvino/` and committed, matching this
  repo's existing fixture convention and keeping tests offline. A manifest alongside them records
  the upstream tarball URL, SHA256, and coupled OpenVINO version, so the coupling survives even
  though the bytes are vendored.
- **Parity is a tolerance check.** `out.bin` is the *eager* golden, not the delegate's output.

### Out of scope, permanently

Everything AOT — export, `OpenvinoPartitioner`, `OpenVINOQuantizer` — all of which require torch,
the one dependency this package exists to avoid. Also out: non-CPU OpenVINO devices (the fixture is
`CompileSpec("device", b"CPU")` and CPU is the only plugin upstream ships), and vendoring the
OpenVINO runtime into the wheel.

### Open questions for C's own cycle

1. **When is `OPENVINO_LIB_PATH` set?** Mutating `os.environ` at import imposes a side effect on
   every user, including those who never touch OpenVINO. But loading happens once under
   `std::call_once` with no retry, so a late fix leaves the process broken until restart.
   Import-time side effect vs. explicit opt-in call vs. lazy-at-first-load is C's central decision.
2. **Per-platform backend divergence.** `registered_backends()` begins differing across wheels, so
   `tests/test_meta_info.py` assertions become platform-conditional, and both the
   `CMakeLists.txt:35` required-target check and the nm registration guard must treat OpenVINO as
   conditional rather than missing.
3. **CI ISA sensitivity.** Upstream hit this directly (`ea393da`, "make the OpenVINO correctness
   stage independent of the runner's ISA"); our linux-x86_64 job will meet the same wall.
4. **Fixture/runtime version coupling on re-roll.** OpenVINO versions independently of ExecuTorch,
   so an OV re-roll can invalidate the committed fixture with no ET bump. The manifest records the
   coupling; what *enforces* it is C's problem.
5. **Behaviour on unsupported platforms.** What a user asking for OpenVINO on aarch64 or Windows
   sees, and whether the extra is declared at all there.
